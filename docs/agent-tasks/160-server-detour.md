## 3. 앱이 읽을 필드 (계약)
`alternatives: {"meal"|"outing"|"cafe": [Alternative, ...]}` — `Alternative`는 `Place`의 모든 필드 + 아래 두 필드.

| 필드 | 타입 | 의미 |
|---|---|---|
| `distance_m` | int 또는 null | 교체 대상(지금 코스의 같은 역할 장소)에서 후보까지 **직선거리(m)**. "0.6km" 표시에 쓴다 |
| `detour_minutes` | int 또는 null | 지금 장소 대신 이 후보로 바꿨을 때 **앞 지점 → 후보 → 뒤 지점** 이동 시간이 지금보다 몇 분 늘어나는지. 음수면 오히려 줄어든다. "경로에서 +2분" 표시에 쓴다 |

- 둘 다 null: 코스에 그 역할 장소가 없을 때(예: 귀가 시각 때문에 카페를 뺀 경우의 카페 후보). 앱은 지금처럼 어림값을 쓰면 된다.
- 앞 지점은 바로 앞 경유지(첫 경유지면 출발지), 뒤 지점은 바로 뒤 경유지(마지막이면 귀가 지점).
- 계산 방식: 외부 호출 없이 직선거리 × 도로 계수 1.4, 30km/h로 추정한 뒤, 지금 코스 전체의 실제 길찾기 시간(카카오) ÷ 추정 시간 비율(0.5~2.0으로 제한)을 곱해 보정한다. 막히는 날이면 우회 시간도 그만큼 크게 나온다. 구간 하나로 비율을 잡으면 1분짜리 짧은 구간 때문에 값이 두 배로 부풀어서(실데이터 확인) 코스 전체 비율을 쓴다.
- 앱이 후보를 골라 `/course/schedule`의 `stops[].place`로 그대로 보내도 된다(서버는 `Place`에 없는 필드를 무시한다).

## 4. 결정과 미정
- **후보 전용 모델 `Alternative(Place)`**를 둔다. `Place`에 필드를 더하면 요청(`ScheduleStop.place`)과 코스 경유지(`Stop.place`)에도 의미 없는 필드가 생기기 때문. 응답 JSON은 기존 필드 그대로 + 두 필드라 기존 앱과 호환된다.
- **카카오 길찾기를 더 부르지 않는다.** 후보 3개 × 역할 3개를 길찾기로 재면 코스 하나당 최대 9번 늘어난다. 추정 + 실제 경로 비율 보정으로 대신한다.
- **재계산 뒤 나들이 후보**: 출발지 기준 나들이 후보 순위(`_rank_outings`)를 다시 계산해, 코스에 이미 있는 곳을 빼고 점수 순 상위 3곳을 준다. TourAPI·카카오 응답은 서버 메모리 캐시(6시간·1시간)에 있어 직전 `/course`와 같은 출발지·조건이면 외부 호출이 늘지 않는다. 실패해도 재계산은 나온다(나들이 후보만 비움).

## 6. 확인하지 못한 것
- 앱 화면에서 값이 보이는 모습(앱 쪽은 이 작업 범위 밖).
- 우회 분은 추정이다. 카카오 길찾기로 후보별 실제 경로와 비교하지는 않았다(호출 수 때문에 의도적으로 하지 않음).
- `suggest_nearby=false`인 재계산은 지금처럼 `alternatives`를 비워 준다. 앱이 이전 후보를 그대로 쓰면 순서를 바꾼 뒤의 우회 분은 옛 값이다. 새 값이 필요하면 `suggest_nearby=true`로 부른다.
- 재계산 뒤 나들이 후보는 점수 순 상위 3곳이라, 처음 `/course`의 가중 무작위 순서와 다를 수 있다.
