## 1. 요약

### 한 줄 요약
**[기획서]** 영유아 동반 가족의 조건과 차량의 위치·에너지 상태, 날씨·장소 정보를 종합해 **식사 → 나들이 → 카페 → 귀가**로 이어지는 하루 전체 코스를 설계하고, 주행 중 상황 변화에 맞춰 일정을 조정하며, 방문 경험을 아이의 성장 기록(경험 맵)으로 축적하는 **차량 기반 AI 원데이 트립 플래너**.

### 앱 컨셉
**[기획서]**
- 포지셔닝: "영유아 동반 가족을 위한 차량 기반 AI 원데이 트립 플래너"
- 기획 방향: 장소 단건 추천을 넘어 **하루 전체 여정을 설계**하는 서비스
- 핵심 경험: 가족 맞춤 코스 설계 · 차량 기반 이동 지원 · 아이 경험 기록
- 핵심 입력: 가족·아이 정보, 출발 위치, 희망 시간·테마, 차량 연료/배터리 상태, 날씨
- 핵심 출력: 식사·나들이·카페·귀가 코스, 장소별 편의정보, 전체 이동거리·시간, 주유/충전 경유안
- 차량 특화 요소: 차량 위치 · 주행 가능 거리 · 내비게이션 경로/도착 이벤트 · 공조 제어(지원 범위 확인 필요)
- 반복 사용 구조: 방문 기록 → 아이 경험 맵 → 새로운 장소 및 재방문 추천
- 핵심 차별화 3가지: ① 하루 전체 코스 설계 ② 차량 상태(연료·배터리)를 반영한 이동 계획(주유·충전 경유 포함) ③ 이동과 경험의 연결(주행 중 변화 대응 + 도착 기록 → 경험 맵 → 다음 추천)
- 기획서가 강조하는 포인트: 차량 에너지 데이터로 장소를 **제한**하는 것이 아니라, 필요하면 주유소·충전소까지 포함해 **실제로 다녀올 수 있는 전체 코스**를 설계한다는 것

### 타깃 사용자
**[기획서]**
- 주 사용자: 영유아 또는 어린 자녀를 둔 가족 운전자. 주말·휴일에 차량으로 외출하며, 아이 연령·동반 조건에 맞는 장소를 찾고 하루 일정을 효율적으로 구성하고 싶은 사용자
- 보조 조건(프로필 입력 항목)
  - 가족 구성: 성인 동반 인원, 아이 연령대, 반려동물 동반 여부
  - 나들이 선호: 자연·체험·전시·놀이, 식사·카페 선호
  - 일정 조건: 출발 시각, 귀가 희망 시각, 희망 총 소요시간
  - 육아 편의: 수유실, 기저귀 교환대, 유아 의자, 유모차 진입, 키즈 메뉴 등
- 대표 시나리오 페르소나: 토요일 오전, 성인 2명 + 18개월 아이, 자연 체험 선호, 오후 6시 전 귀가 희망, 주유 경유가 필요할 수 있는 에너지 상태

### 해결하려는 문제
**[기획서]** 핵심 문제 정의: "아이와 함께하는 주말 외출에서 가족은 장소 하나가 아니라 하루 전체의 실행 가능한 동선을 필요로 하지만, 현재는 장소 탐색·육아 조건 확인·차량 이동 계획·일정 변경을 각각 해결해야 한다."

| 사용자 불편 | 현재의 번거로움 | 서비스 해결 방향 |
|---|---|---|
| 일정 구성 부담 | 식당·체험 장소·카페를 각각 검색하고 동선을 직접 조합 | 하루 전체 코스를 한 번에 구성 |
| 아이 동반 조건 확인 | 수유실, 유아 의자, 유모차 진입 등을 여러 채널에서 확인 | 장소별 육아 편의정보를 일정 추천에 반영 |
| 차량 상태 고려 부족 | 현재 연료·배터리로 왕복 가능한지 별도 판단 | 전체 코스의 예상 이동거리·에너지와 주유/충전 경유를 함께 계산 |
| 계획 변경의 번거로움 | 비·정체·운영시간 변화 시 일정을 다시 검색 | 이동 중 변화에 맞춰 대체 장소와 코스 재구성 |
| 경험의 단절 | 방문 기록이 흩어져 다음 나들이에 활용되지 않음 | 아이 경험 맵에 축적하고 재추천에 활용 |

기획 목표(4가지): 가족·아이 조건 맞춤 코스 일괄 제안 / 차량 위치·에너지 반영으로 실행 가능성 제고 / 주행 중 변화 대응으로 변경 부담 감소 / 방문 경험 기록·재추천으로 반복 사용 이유 창출

## 2. 핵심 기능 목록 및 우선순위

### 2-1. 기획서에 적힌 기능 (원문 정리)

**F1. AI 원데이 패밀리 코스 자동 설계 (4-1)** [기획서]
- 테마·시간 조건 입력 → 식사 → 나들이 장소 → 카페 → 귀가 코스 구성
- 장소 유형별 후보 수집 후 운영시간, 아이 편의시설, 장소 간 이동시간, 체류시간, 전체 일정 길이를 고려해 조합
- 코스 테마: 자연·체험·전시·놀이·반려동물 동반 등
- 장소 구성: 식사 장소, 메인 나들이 장소, 카페(필요 시 경유지 추가)
- 장소별 정보: 장소명, 주소, 운영시간, 예상 체류시간, 아이 편의시설, 반려동물 동반 여부
- 일정 정보: 장소 간 이동시간, 전체 이동거리, 예상 귀가시간, 코스 총 소요시간
- 사용자 편집: 특정 장소만 교체하면 전체 경로와 시간 재계산

**F2. 차량 에너지 기반 코스 구성 (4-2)** [기획서]
- Fuel 또는 EvBattery의 연료·배터리 잔량 및 예상 주행 가능 거리로 전체 일정의 이동 가능성 판단
- 코스 유형 3가지
  - 바로 출발 가능한 코스: 주유·충전 없이 다녀올 수 있는 일정 ("현재 차량 상태로 이동 가능한 코스")
  - 주유·충전 경유 코스: 경로상 주유소·충전소를 포함 ("주유소 1곳 경유 / 충전소 1곳 경유")
  - 에너지 정보 부족: 주행 가능 거리 또는 충전소 실시간 정보가 없으면 보수적으로 안내 ("차량 에너지 정보 확인 필요")
- 경유지 선택 기준: 가장 가까운 곳이 아니라 전체 코스에서 우회가 적고 목적지·귀가까지 이동 가능한 위치 우선
- EV는 충전기 종류·운영 상태·가용 여부를 확인할 수 있을 때만 실시간 사용 가능 정보 제공

**F3. 베이비 케어 모드 (4-3)** [기획서]
- 보호자가 설정한 차량 실내 환경을 간편하게 불러오고 조절. 기존 원격 공조와 구분되는 "영유아 동반 나들이용 프리셋"
- HVAC: 지원 시 실내 온도·풍량·공조 상태 조회 및 제어
- Light: 지원 시 실내 조명/앰비언트 라이트 설정
- Window: 창문 상태 확인(제어 지원 여부 및 주행 중 제한 확인)
- 프리셋: 보호자 선호 설정값 저장·불러오기
- 제약: 아이에게 적합한 온도를 의학적으로 판단하지 않음, 아이를 차량에 혼자 둔 채 공조로 관리하는 시나리오 미제공

**F4. 이동 중 나들이 플랜 변경 (5-1)** [기획서]

| 변화 상황 | 판단 로직 | 서비스 대응 |
|---|---|---|
| 날씨 변화 | 목적지 도착 예정 시점의 강수·기온 확인 | 야외 → 실내 대체 장소 제안 |
| 교통 정체 | 예상 도착시간 및 전체 일정 지연 확인 | 가까운 대체 장소 또는 일정 순서 변경 제안 |
| 운영시간 임박 | 예상 도착시간과 입장 마감·영업 종료 비교 | 운영 중인 대체 장소 제안 |
| 에너지 여유 부족 | 남은 일정의 예상 주행거리·에너지 재검토 | 주유·충전 경유 추가 또는 코스 조정 |
| 사용자 요청 | 음성 또는 정차 후 화면 입력 | 특정 장소 교체 및 전체 동선 재계산 |

**F5. 우리 아이 경험 맵 (5-2)** [기획서]
- 내비 목적지 도착 이벤트 → 방문 기록 후보 생성 → 보호자 확인 → 경험 맵 반영
- 경험 분야 분류: 자연·체험·전시·놀이 등
- 차량 인포테인먼트: 총 방문 장소 수, 분야별 경험 요약, 다음 추천 1~3건 (주행 중 빠르게 확인할 요약)
- 모바일 앱: 방문 장소·날짜·아이 당시 연령·경험 분야·사진·메모·방문 상태 (상세 기록·추억 관리)
- 도착 이벤트만으로 시설 이용을 확정할 수 없으므로 최초 기록은 "방문 기록 후보"로 저장 (주차장 도착 후 미방문 케이스 고려)

**F6. 경험 기반 재추천 (5-3)** [기획서]
- 새로운 경험: 방문 이력이 적거나 없는 분야 + 가족 선호 (예: 자연·체험이 많으면 전시 제안)
- 재방문 추천: 아이 성장, 계절 변화, 신규 프로그램, 재방문 가치 (예: 어릴 때 간 동물원의 연령별 신규 체험)
- 지금 가기 좋은 곳: 현재 날씨·시간·이동거리·차량 에너지·운영 여부 (예: 오늘 조건에 맞는 가까운 실내 체험)
- 원칙: 경험 횟수가 적은 분야를 "부족한 경험"으로 단정하지 않음, 새로운 경험과 재방문을 균형 있게 제안

**F7. 차량 위치·내비게이션 연결** [기획서, 7장/9장]
- FusedLocation으로 현재 위치 수신 및 탑승 시 추천 시작
- NaviHelper로 목적지 설정, 경로 시작·변경·도착 이벤트 수신, 다음 장소를 일정 순서에 따라 안내

**F8. 음성 인터페이스** [기획서, 7장]
- SpeechToText/TextToSpeech: 주행 중 음성 요청 및 간단 안내
- Gleo Interface: 음성으로 코스 요청 및 추천 기능 호출

### 3-2. 대표 이용 시나리오 8단계 (기획서 6장)
**[기획서]**
1. 탑승 — "오늘 나들이 코스" 선택 → FusedLocation으로 현재 위치 확인, 가족 프로필·선호 조건 로드
2. 출발 준비 — 베이비 케어 모드 선택 → 지원되는 HVAC 설정값 확인·적용, 차량 에너지 정보 표시
3. 코스 제안 — 자연 체험 테마, 귀가 희망시간 확인 → 식당·수목원·카페·귀가 조합, 전체 이동거리·시간 계산
4. 에너지 확인 — 추천 코스 중 하나 선택 → 에너지 충분 여부 판단, 필요 시 경로상 주유소/충전소 포함
5. 길 안내 — 코스 시작 → 내비게이션에 첫 목적지 설정, 다음 장소는 일정 순서에 따라 안내
6. 이동 중 변경 — 목적지 주변 강수 예보 변화 → 실내 대체 장소와 일정 변경안을 음성으로 제안
7. 도착 기록 — 나들이 장소 도착 → 도착 이벤트로 방문 기록 후보 생성, 보호자 확인
8. 다음 주말 — 다시 탑승 → 경험 맵·최근 방문 이력 반영해 새로운 경험 또는 재방문 코스 추천

## 4. 차량 / Pleos 플랫폼 연동 지점

### 4-1. 기획서에 명시된 것
**[기획서]** 권장 구조: 차량 앱(PLEOS Connect/AAOS) → 서비스 서버 → 외부 공공·민간 API. 차량 앱은 차량 SDK와 인포테인먼트 UI, 서버는 외부 API 인증·호출, 장소 데이터 정규화, 추천 점수 계산, 일정 최적화 담당.

| SDK/API | 활용 계획 | 기획서가 적은 확인 사항 |
|---|---|---|
| FusedLocation | 차량 현재 위치 수신, 탑승 시 추천 시작 | 권한·수신 주기·에뮬레이터 지원 |
| NaviHelper | 목적지 설정, 경로 시작·변경·도착 이벤트 | 다중 경유지·다음 목적지 연속 안내 지원 여부 |
| Fuel / EvBattery | 연료·배터리 잔량, 예상 주행 가능 거리 | Range를 직접 제공하는지, 잔량만 제공하는지 |
| HVAC | 실내 온도·풍량·공조 상태 조회/제어 | 조회/제어 범위, 프리셋 적용, 원격/주행 중 제어 제한 |
| Light | 실내 조명/앰비언트 라이트 | 지원 여부 |

| Vehicle Wiper | 강우 상황 보조 신호(선택) | 도메인 접근 권한·상태값 제공 범위 |
| SpeechToText / TextToSpeech | 주행 중 음성 요청 및 간단 안내 | 주행 중 UX 제한·지원 언어 |
| Gleo Interface | 음성으로 코스 요청 및 추천 기능 호출 | 운영 환경 및 연동 권한 |
| CarUxRestrictions | 주행 중 화면 조작 제한 적용 | 제한 상태별 허용 UI |

주행 중 UX 제약(기획서 명시):
- 주행 중에는 큰 버튼·짧은 문구·음성 안내 우선, 복잡한 비교·일정 변경 확정은 정차 후
- 복잡한 장소 비교 화면은 주행 중 노출하지 않음
- 교통·날씨 변화만으로 자동 목적지 변경을 실행하지 않고 대체안만 제안, 운전자/보호자가 선택
- CarUxRestrictions로 주행 중 허용되지 않는 입력·화면 차단
- 차량 데이터로 알 수 없는 상황(식사 시간 연장, 아이가 잠듦 등)은 보호자의 음성 요청/일정 수정으로 반영
- 카시트 체결, 아이의 체온·수면 상태 등 API로 확인 불가한 정보를 차량이 감지한다고 표현하지 않음

시연 대체 전략(기획서 명시): 실제 차량 제어 API·실시간 충전소 데이터가 미확보되면 시뮬레이터·목업 데이터로 시연하고 "실제 API 연동 전제/확인 필요"로 구분 표기. 실제 구현과 시뮬레이션을 혼동해 표현하지 않음.

### 4-2. 분석자 추정 (기획서에 없음)
**[추정]**
- 기획서는 "PLEOS Connect/AAOS"라고만 적고 있어, 실제 타깃이 Android Automotive OS 기반 네이티브 앱(Kotlin)인지, 다른 런타임인지는 공모전 제공 SDK 문서로 확인해야 한다. SDK 명칭(FusedLocation, NaviHelper, CarUxRestrictions 등)은 AAOS/Car API 계열 명명과 유사하지만 기획서는 패키지·버전을 적지 않았다.
- 내비게이션 도착 이벤트의 정확도(주차장 vs 시설 입구)가 경험 맵 품질을 좌우한다. 기획서도 이를 인지해 "후보 → 보호자 확인" 2단계를 두었다.
- NaviHelper가 다중 경유지를 지원하지 않을 경우 "목적지별 순차 설정" 방식을 기획서가 대안으로 제시했으나, 그 경우 "다음 목적지로 전환" 트리거(도착 이벤트 수신 → 자동 설정 vs 사용자 확인)의 설계가 추가로 필요하다.
- 차량 앱이 백그라운드에서 도착 이벤트를 받을 수 있는지(앱이 포그라운드가 아닐 때)는 기획서에 언급이 없다.
- 에뮬레이터/시뮬레이터에서 Fuel/EvBattery·HVAC 값을 주입할 수 있는지가 시연 전략의 핵심 전제인데, 기획서는 FusedLocation에 대해서만 "에뮬레이터 지원"을 확인 사항으로 적었다.
- 서버 ↔ 차량 앱 간 인증(계정/가족 프로필 식별)과 모바일 앱 연동 방식은 기획서에 없다.

## 5. 외부 API / 데이터 소스 및 기술 스택 단서

### 5-1. 기획서가 후보로 적은 외부 데이터/API
**[기획서]**

| 데이터 영역 | 후보 소스 | 활용 |

| 날씨 | 기상청 단기예보·초단기실황 | 현재 및 목적지 도착 예정 시점의 날씨 판단 |
| 관광·육아 편의 | 한국관광공사 관광정보·무장애 여행 정보 | 관광지, 편의시설, 장소 분류 |

### 5-2. 기술 스택 단서
**[기획서]**
- 3계층: 차량 앱(PLEOS Connect/AAOS) / 서비스 서버 / 외부 API
- 차량 앱 역할: 차량 위치·내비 이벤트 수신, 차량 화면 표시, 음성 안내, 지원되는 차량 기능 제어
- 서비스 서버 역할: 외부 API 호출·인증 관리, 가족 프로필·경험 기록 관리, 장소 필터링, 코스 생성·재계산
- 모바일 화면(확장): 경험 맵 상세 조회, 방문 기록 확인·수정, 사진·메모 관리
- AI/규칙 역할 분리: **AI는 자연어 요청 이해와 선호·테마 구조화만** 담당. 장소 운영 여부, 경로·거리, 에너지 가능성, 일정 충돌은 외부 API 결과와 규칙 기반 계산으로 검증. 생성형 AI가 확인되지 않은 장소 정보나 충전 가능 여부를 만들어내지 않도록 함
- 추천 파이프라인 8단계: 입력 수집 → 장소 후보 수집 → 필수 조건 필터(정보 없으면 "정보 없음" 표시) → 코스 조합 → 전체 경로 검증 → 에너지 보충 경유 → 순위화·제시 → 주행 중 재계산
- 추천 점수 요소 6가지: 가족 적합도, 이동 효율, 운영 적합도, 차량 적합도, 경험 적합도, 일정 적합도

**[추정]** 기획서에 없는 것: 구체 언어/프레임워크, DB, 서버 호스팅, LLM 제공자/모델, 인증 방식, 모바일 앱 플랫폼. 서버 측은 공공 API 키 보호와 호출 한도 관리를 위해 반드시 필요하며, 코스 조합은 LLM이 아닌 서버의 결정론적 로직(필터 + 스코어링 + 간단한 조합 탐색)으로 구현하는 것이 기획서의 "AI/규칙 분리" 원칙에 부합한다.

**[추정]** 주유소·충전소 데이터 제공처 후보: 기획서가 비워둔 항목이다. 국내에서는 한국석유공사 오피넷(주유소), 한국환경공단 EV 충전소 정보(공공데이터포털) 등이 일반적으로 알려진 소스이나, 기획서에 명시된 것이 아니므로 팀 확인 필요.

## 6. 구현 리스크 · 모호한 부분 · 개발 전 결정 사항

### 6-1. 구현 리스크
**[기획서가 직접 인지한 리스크]**
- Fuel/EvBattery가 Range를 직접 주는지 잔량만 주는지 불명 → 잔량만 줄 경우 차량별 연비/전비 가정이 필요
- HVAC 조회/제어, 프리셋, 원격/주행 중 제어 제한 미확인 → 베이비 케어 모드가 UI 프로토타입에 그칠 가능성
- NaviHelper 다중 경유지/순차 안내 지원 여부 미확인
- 장소 API가 수유실·기저귀 교환대·유아 의자·유모차 진입 정보를 실제 제공하는지 미확인 → 핵심 차별화(육아 편의 필터)의 데이터 공백 가능성
- 충전소 실시간 가용 상태·충전기 종류·주유소 운영시간 데이터 이용 조건 미확인
- 외부 API 호출 한도·상업적 이용 조건 미확인

**[추정] 추가 리스크**
- **데이터 커버리지**: 식당/카페(카카오 로컬)에는 유아 의자·키즈 메뉴 같은 속성이 구조화되어 있지 않을 가능성이 높다. "정보 없음"이 대부분이면 가족 적합도 점수가 무의미해진다. 자체 큐레이션 데이터셋(시연 지역 한정)이 필요할 수 있다.
- **데이터 조인 문제**: 관광공사 데이터(관광지)와 카카오 로컬(식당·카페), 길찾기(좌표)가 서로 다른 ID 체계를 쓰므로 장소 정규화/중복 제거 로직이 서버에 필요하다.
- **조합 폭발과 응답 시간**: 식당 × 나들이 × 카페 × (주유소) 조합에 각 구간 경로 API를 호출하면 호출 수가 급증한다. 후보 가지치기, 직선거리 선필터, 경로 API 호출 캐싱 전략이 필요하다.
- **주행 중 재계산 트리거 설계**: 날씨·교통 변화를 "언제, 어떤 주기로" 감지할지 기획서에 없다. 폴링 주기와 API 한도가 충돌할 수 있다.
- **도착 이벤트 신뢰도**: 주차장 도착 ≠ 시설 방문. 기획서는 보호자 확인으로 보완하지만, 확인 UX가 주행 중에 뜨면 CarUxRestrictions와 충돌한다(정차 후 혹은 다음 탑승 시 확인으로 미뤄야 함).
- **시뮬레이션 vs 실연동 경계 관리**: 심사에서 "실제로 되는 것"과 "목업"을 명확히 구분해야 한다는 기획서 원칙을 코드/데모 레벨에서 어떻게 보여줄지(예: 모의 데이터 배지) 정해야 한다.
- **개인정보**: 아이 생년월일 최소 처리, 위치·방문 기록 보관 기간·동의 — 기획서가 원칙만 적고 구체 구현(동의 화면, 삭제 기능)은 없다.
- **EV/내연기관 분기**: Fuel과 EvBattery 중 어느 쪽인지 차량별로 분기해야 하며, 두 케이스 모두 시연할지 하나만 할지 미정.
- **음성(Gleo/STT/TTS) 의존도**: 주행 중 UX가 음성 중심인데, Gleo Interface의 "운영 환경 및 연동 권한"이 미확인이면 주행 중 플랜 변경(P1)의 핵심 입력 경로가 막힌다.

### 6-2. 기획서상 모호하거나 빠진 부분
**[추정]**
- 와이어프레임/화면 설계 전무 (흐름 표만 존재)
- 가족 프로필을 "어디서, 언제" 입력하는지 (차량에서 정차 중? 모바일에서 먼저?) 미정
- 계정/가족 식별 체계 (차량 앱과 모바일 앱이 같은 가족 데이터를 보는 방법) 없음
- "코스 테마" 선택 UI와 자연어 입력(AI) 중 1차 시연의 기본 입력 방식 미정
- 코스 추천 개수(상위 N개), 체류시간 기본값(장소 유형별) 미정
- "에너지 정보 부족" 상태에서의 구체 동작(코스는 보여주되 경유 판단만 생략? 아예 보수적 반경 제한?) 미정

- 모바일 앱의 범위(네이티브? 웹? 공모전 제출 범위 포함 여부) 불명

### 6-3. 개발 전에 결정해야 할 질문
**[기획서 12장 "팀 회의에서 결정할 항목" (원문)]**
1. 1차 시연에서 코스 유형을 식사–메인 나들이–카페–귀가로 고정할지, 사용자가 장소 유형을 추가·삭제하도록 할지
2. 아이 편의시설 중 필수 필터로 둘 항목(수유실, 기저귀 교환대, 유아 의자, 유모차 진입 등)
3. 차량 에너지 API가 제공하는 실제 값과 주유·충전 경유 코스의 계산 범위
4. 경험 맵을 차량 요약 화면과 모바일 상세 화면으로 나누는 구조
5. 실제 API 연동과 시뮬레이션으로 시연할 기능의 경계
6. 코스 추천 시 AI 활용 범위와 자체 일정 최적화 로직의 역할

**[기획서 10장 "개발 전 필수 확인 사항" (원문)]**
- Fuel/EvBattery API가 Range를 직접 제공하는지, 잔량만 제공하는지
- HVAC의 온도·풍량 조회/제어, 프리셋 적용, 원격/주행 중 제어 제한
- NaviHelper 다중 경유지 또는 순차 안내 가능 여부 (미지원 시 목적지별 순차 설정으로 설계)
- 장소 API의 육아 편의정보 실제 제공 여부 (누락은 "정보 없음")
- 충전소 실시간 가용 상태, 충전기 종류, 주유소 운영시간 및 데이터 이용 조건
- 주행 중 화면 조작 제한과 음성 안내 정책 준수

**[추정] 분석자가 추가로 제안하는 결정 질문**
7. 타깃 런타임·언어 확정: Pleos SDK가 요구하는 앱 형태(AAOS 네이티브 Kotlin? 웹 기반?)와 최소 SDK 버전
